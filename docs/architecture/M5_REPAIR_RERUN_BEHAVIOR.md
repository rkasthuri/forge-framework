# M5 Chunk 5: governed repair rerun

This contract extends the existing [ExecutionService](../../src/core/execution/ExecutionService.ts), [ExecutionRepository](../../src/core/storage/repositories/ExecutionRepository.ts), and [ExecutionRunCoordinator](../../src/core/execution/ExecutionRunCoordinator.ts). It preserves [ADR-024](../ADR/ADR-024-execution-service-as-sole-runner-invocation-boundary.md), [ADR-025](../ADR/ADR-025-execution-run-and-test-result-authority.md), [Chunk 4](M5_REPAIR_MATERIALIZATION_BEHAVIOR.md), and the frozen [M5 evidence schemas](../../fixtures/m5-contract/manifest.json).

## Acceptance contract

1. Input is an explicit `repair_rerun` execution selection: the exact Chunk 4 materialization request; expected resulting Definition authority (including exact Test Set row, revision, canonical fingerprint and historical Definition hash); and exact original Execution, Run, Result, manifest ordinal, plan hash and diagnostic evidence identity/hash. Runtime and credential reference remain ephemeral execution inputs. A project-scoped execution intent key retains canonical duplicate-control ownership.
2. The subject is the one canonical v3 Definition in the exact materialized Test Set. No new Suite is created. Exact inactive App Model revisions remain eligible: historical committed candidate/support/route authority, not current Test Set or active-model selection, determines this repair subject. Existing canonical plan projection and hash producers own executable meaning.
3. Read preflight and transactional acceptance revalidate separately committed approval, supersession, proposal, proposal-identity witness, source execution-item witness, both App Model revisions, source Definition, exact regenerated materialization, and actual source Result/diagnostic provenance. Missing, malformed, conflicting or stale authority refuses before new lifecycle writes. Caller objects never substitute for persisted authority.
4. The original evidence must be a terminal canonical non-passing Result with exact diagnostic evidence and accepted source Definition identity. Canonical selector/action failures can be `could_not_verify`; this contract never relabels them `failed`. Passing Results, absent Results, cancelled-without-Result and unrelated failures cannot become supplied original failed evidence. Diagnostic interpretation and integrity remain owned by existing M4 producers/readers. The exact original Result and its terminal Execution event must predate or equal the proposal time. Completed, cancelled or interrupted lifecycle can supply an already persisted non-passing Result; lifecycle never fabricates missing evidence. The frozen diagnostic row has no independent recorded timestamp, so this contract verifies its exact existing content/hash and does not claim an unrecorded diagnostic creation time. The new binding records the supplied, verified historical relationship; because the frozen proposal has no diagnostic field, it does not assert retroactively that this diagnostic caused the earlier proposal or was separately attested by the human approver.
5. A minimal immutable acceptance relation connects the new Execution to the exact materialization and original evidence. It is part of the existing Execution acceptance transaction together with the root, manifest, item authorities, lock and started event. Reciprocal references and exact SQL guards prevent detached or conflicting acceptance. Caller-owned transactions cannot combine uncommitted upstream authority with acceptance.
6. `ExecutionService` remains the sole Product caller of the existing executor. After acceptance commits, the existing Run coordinator admits at most one Run with attempt ordinal 1. There is no queue, new retry scheduler, second executor, or M5 Result type.
7. The existing Run coordinator appends canonical Result and diagnostic evidence. For a governed repair acceptance, it also appends the existing frozen `repair_rerun_links` record in the same transaction. Result and link cannot partially commit. The link uses existing M5 link hashing; Test Set, Definition, diagnostic and plan hashes remain with their existing producers.
8. Lifecycle remains canonical: accepted/running, optional cancellation requested, and completed/cancelled/interrupted, with evidence outcome separate from lifecycle. A structured failed execution preserves a new immutable Result. A thrown adapter error, failed Run admission, failed Result transaction or cancellation before evidence never fabricates a Result. Existing on-contact recovery handles durable acceptance/Run state and manifest gaps; the immutable acceptance relation preserves provenance even when no Result exists.
9. Exact resubmission returns the same Execution and never invokes the executor again. Conflicting request semantics under the same intent key refuse. Repair replay revalidates its stored binding and available exact upstream authority; invalid or unavailable repair/source authority refuses rather than creating a replacement attempt. A new explicitly distinct intent may create a separately identified execution under existing project concurrency policy. No automatic retry or repair-effectiveness decision exists.
10. The provenance path is new Result -> existing rerun evidence link -> new Execution and immutable repair acceptance -> exact Chunk 4 output/origin -> supersession -> committed human approval/proposal/witness -> source Definition and explicitly bound original Execution/Run/Result/diagnostic. Original Definition, Test Set, Execution, Result, diagnostic, Suite, and upstream repair authority are unchanged.
11. Ordinary direct and Suite execution retain their existing canonical semantics. They do not claim the new governed repair acceptance. The frozen historical `persistRerunExact` API remains evidence admission after real execution; it does not authorize or initiate execution. New public/repository selection parameters cannot be used to smuggle unchecked governed acceptance through these ordinary paths. Frozen historical direct/Suite linkage schemas and fixtures remain unchanged.
12. Input shape/integrity errors precede missing authority. Existing Chunk 4 refusal precedence and counts survive exact materialization checks. Original-evidence mismatches refuse as source authority failures. Intent conflicts remain distinct from stale authority, active execution and persistence failures. Invalid acceptance leaves no new authoritative state; post-acceptance failure retains only legitimately committed canonical history for existing recovery.

## Scope and limits

No before/after comparison, repaired/not-repaired judgment, retaining a repair, new proposal, UI, Suite materialization, autonomous approval/healing, ranking, LLM candidate choice, credentials, or infrastructure repair belongs to this chunk. Local single-host execution and its existing process-local cancellation/recovery limits remain explicit. Existing witness independence is bounded to independently admitted evidence and existing single-record corruption checks; this work does not claim protection against coordinated arbitrary database rewriting.

Validation covers real canonical execution wiring, exact Result/diagnostic reread, hostile public/repository inputs, original-history preservation, replay/conflict/cancellation/recovery, transactional faults, SQL binding guards, native/WASM upgrade/reopen, M3/M4/M5 and execution regressions, canonical units, TypeScript, headers, diff and clean-checkout integrity. Live storage unavailable is never reported as certified by disposable tests.
